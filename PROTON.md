# Kiln: «Протон для Майнкрафта»

Живой документ: видение, этапы, риски и всё, что мы узнаём про Horizon по ходу работы. Решения — в [DECISIONS.md](DECISIONS.md).

## Видение

Игрок скачивает Java-мод (`.jar`), кладёт его в папку, запускает [Horizon](https://github.com/horizon-rust/horizon) — Minecraft: Java Edition 26.3, переписанный на Rust, — и мод работает. Как Proton запускает Windows-игры на Linux: чужой код выполняется как есть, а его вызовы к «системе» (здесь — к классам Майнкрафта и Fabric API) переводятся в вызовы Horizon.

Для игрока:
1. Один раз ставит мод **Kiln** из лаунчера Horizon. Лаунчер один раз пересобирает игру (20–30 минут, с предупреждением) — так устроены все нативные моды Horizon.
2. Кладёт `.jar`-моды в папку Kiln.
3. Играет. Новые jar-моды не требуют пересборки (если выполнять их во время игры; см. «Как Kiln выполняет Java»).

## Почему Kiln — нативный мод

- **WASM-моды из Horizon удаляют** (issues #3350, #3351, #3353, #3371; ROADMAP: «then the WebAssembly runtime is removed»). Остаются контент-моды (только данные) и нативные моды.
- **Песочнице WASM не хватало доступа.** Её API: HUD-текст, чат, позиция игрока, хранилище, команды. Java-модам нужны мир, сущности, блоки, рендер, экраны, сеть.
- **Нативный мод видит всю игру.** Helper получает `&mut Game`, а модули бандла — дочерние модули `crate::game`, поэтому им видны его поля. horizon-mixins по сути Rust-аналог Mixin: HEAD, RETURN, BEFORE_CALL, MODIFY_ARG, OVERWRITE по функциям игры.

Цена: игрок играет в сборке, которую лаунчер сделал с модами, а не в официальной сборке (DECISIONS.md, D-002).

## Почему задача вообще решаема

- **Майнкрафт с 26.1 не обфусцирован** (`docs/version-ports.md` в Horizon: «since 26.1 ship unobfuscated»). Java-моды под 26.x обращаются к классам по настоящим именам: `net.minecraft.client.Minecraft`, `PlayerList`…
- **Исходники Horizon размечены теми же именами:** комментарии вида `Minecraft.tick`, `LevelLoadingScreen.tick`, `PlayerList.broadcastSystemMessage`. Таблица соответствий «Java-класс и метод → функция Horizon» получается почти механически.
- **В Horizon уже есть чтение zip** (крейт `zip` в зависимостях `horizon-client`), то есть и jar-файлов.

## Как Kiln выполняет Java

| | Как | Плюсы | Минусы |
|---|---|---|---|
| 1 | **Настоящая JVM внутри игры** через JNI (`dlopen` libjvm, таблица JNI вручную — внешние крейты в бандле недоступны) | Полная совместимость Java, рефлексия, JIT; библиотеки Майнкрафта (Gson, Guava, fastutil) грузятся как есть. Java у игрока уже есть: лаунчер Horizon ставит её для подготовки | Встраивание JVM в процесс на Rust (сигналы, потоки, три ОС); заглушки классов нужно где-то брать (в `.hnmod` можно класть только `.rs` и `.toml`); ревью мейнтейнеров может не пропустить |
| 2 | **Свой интерпретатор байткода на Rust** | Всё в читаемом Rust, без внешней JVM; классы Майнкрафта — сразу Rust-функции | Стандартную библиотеку Java и библиотеки Майнкрафта придётся интерпретировать или писать самим; медленнее |
| 3 | **Компилятор jar → Rust-код**, лаунчер собирает его как нативный мод | Быстро работает, вписывается в конвейер лаунчера | Самый сложный в разработке; пересборка игры на каждый мод |

Спайк этапа 1 начинаем с варианта 1, запасной — 2 (D-007).

**Откуда брать заглушки классов при варианте 1** (открытый вопрос):
- (а) генерировать байткод заглушек из Rust (маленький писатель class-файлов);
- (б) скачивать jar заглушек из нашего релиза с проверкой SHA-256 (в Horizon есть `ureq`);
- (в) класть рядом с бандлом при локальной сборке (`horizon-launcher native-build FOLDER`).

## Результаты спайка

### 2026-10-29: JVM внутри программы на Rust, без крейтов (`spike/jvm-embed/`)
Отдельная программа с теми же ограничениями, что у модуля нативного мода: только `std`, JNI вручную (`dlopen` libjvm, функции по индексам таблицы `JNINativeInterface_`). Mac mini, Apple Silicon, release-сборка.

| | Temurin 25.0.2 | Java из лаунчера Minecraft (Mojang 21.0.7) |
|---|---|---|
| Запуск JVM | 20 мс | 236 мс (холодный) |
| `init` мода: рефлексия, лямбда, stream, вызов Rust из Java | 9 мс | 20 мс |
| Вызов Rust → Java → Rust со строкой | 286 нс | 308 нс |
| 100 000 NullPointerException в горячем цикле (JIT, неявные null-проверки через SIGSEGV) | 55 мс, без падений | 53 мс, без падений |

Выводы:
- Вариант 1 жизнеспособен: JVM встаёт в процесс на Rust, вызовы идут в обе стороны (`RegisterNatives`), рефлексия работает.
- Обработчики сигналов HotSpot уживаются с обработчиком Rust.
- Вызов в сотни раз дешевле бюджета кадра (0,1 мс).
- Локальные ссылки JNI нужно освобождать вручную (`DeleteLocalRef` или `PushLocalFrame`/`PopLocalFrame` на каждый хук): из игры мы вызываем Java без Java-кадра вокруг, и ссылки иначе копятся.

Дальше: тот же код — модулем Kiln внутри Horizon.

### 2026-10-29: внутри Horizon `unsafe` запрещён → Java в отдельном процессе
- **Находка:** `crates/horizon-client/src/main.rs` и `lib.rs` начинаются с `#![forbid(unsafe_code)]`. Модули нативного мода встраиваются в этот крейт, а `forbid` нельзя снять даже `#[allow]` на своих функциях. Значит, без правки исходников Horizon в процессе игры нельзя ни `dlopen`, ни JNI, ни любой FFI. **Вариант 1 (JVM внутри процесса игры) закрыт** ограничением «не менять Horizon».
- **Обход внутри правил (вариант 1б):** Kiln запускает Java отдельным процессом (`std::process::Command`, безопасный Rust): `java -cp kiln-runtime.jar:<моды> kiln.Host`. Общение — строки через stdin/stdout (протокол в `kiln/java/kiln/Host.java`). Ответы Java читает отдельный поток в канал, игра на каждом тике только пишет строку и забирает готовые ответы, то есть **никогда не ждёт Java**.
- **Замеры** (`kiln/tests/java_mods.rs`, Temurin 25, Apple Silicon):

| | |
|---|---|
| От первого тика до строки мода на HUD (запуск Java + `onInitializeClient`) | 42 мс, игра не ждёт |
| Цена тика для игры | 1,7 мкс |
| Ответ Java на тик (тик ушёл → строка HUD пришла) | медиана 0,03 мс, худший 1,2 мс |

- **Плюсы:** падение или зависание Java не роняет игру; нет конфликта сигналов; один код на всех ОС; рефлексия и вся Java как есть.
- **Минусы:** ответы Java видны со следующего тика; синхронные вопросы Java к игре (`player.getX()`) нельзя задать «вживую», их приходится отвечать из снимка состояния, который Kiln присылает с каждым тиком (как делал WASM-API Horizon); отдельный процесс занимает память (`-Xmx512m`).
- `cargo check` внутри Horizon проходит (`native.py check kiln`).

### Как Kiln будет видеть состояние игры (для horizon-bridge)
Через hook points этого не получить, но модули Kiln — дочерние модули `crate::game`, поэтому им видны внутренние поля `Game` (чтение, без правки кода):
- `game.adv.tree.by_id` → индекс → `game.adv.progress.done(&game.adv.tree.list[i])` — получено ли достижение;
- `game.pause`, `game.title`, `game.loading_reason()` — пауза, титульный экран, загрузка;
- `game.world.game_time` — игровое время мира;
- `game.acting_player_name()` — свой ник.

Риск — переименования в новых Nightly (D-008).

Отличие от ванилы, которое Kiln должен скрывать: в ваниле клиентский тик (`ClientTickEvents.END_CLIENT_TICK`) идёт и на паузе, а в Horizon `native_tick` на паузе не вызывается. Kiln должен досылать Java-модам тики из `native_frame` 20 раз в секунду. Это и есть работа «переводчика».

### 2026-10-29: таймер-jar работает в Horizon через Kiln
`kiln/proof.py` (игра без окна на временных данных, `horizon-ctl`): новый мир → Kiln запускает Java и два Fabric-мода; таймер стартует сам; `advancement grant` и `execute in … run tp` дают все шесть сплитов; двухсекундная пауза и загрузки измерений не входят в IGT (IGT 0:20.2 при RTA 0:22.4); «Free the End» финиширует ран, рекорды сохраняются; клавиша U прячет панель.

Устройство моста (horizon-bridge) — три слоя:
- **Rust, состояние игры** (`kiln/mixins/kiln/horizon.rs`): пауза, игровое время, измерение, достижения, ширина символов шрифта. Только чтение.
- **Rust, протокол** (`runtime.rs`, `jvm.rs`): на каждом тике — строки `key`, `adv`, `tick` в Java; в ответ — `draw` (что мод рисует), `chat`, `log`. Тики идут и на паузе и на титульном экране (из `native_frame`), как у ванильного клиента.
- **Java, заглушки** (`kiln/java/`): `Minecraft`, `ClientLevel`, `LocalPlayer`, `ClientPacketListener`, `ClientAdvancements`, `Font`, `GuiGraphicsExtractor`, `KeyMapping`, `InputConstants`, `Identifier`, `ResourceKey`, `Component`; Fabric: `ClientModInitializer`, `Event`, `ClientTickEvents`, `HudElementRegistry`, `HudElement`, `KeyMappingHelper`, `FabricLoader`.

Что узнали:
- **Коды клавиш в Minecraft 26.x — скан-коды USB HID** (`KEY_A = 4`, `KEY_F1 = 58`), а не GLFW. Моды вшивают эти константы в свой байткод, поэтому заглушка обязана совпадать.
- **В 26.3 `ClientAdvancements.progress()` публичный**: мод читает достижения без Mixin.
- **`GuiGraphics` в 26.x называется `GuiGraphicsExtractor`**, а HUD-элементы Fabric — `HudElement.extractRenderState`. Цвет текста — ARGB, альфа 0 не рисуется.
- **Клиентская копия достижений в Horizon после смены измерения почти пуста** (D-023). Сервер одиночной игры хранит прогресс у игрока в `lan.hub.guests`.
- **Во время смены измерения в Horizon нет игрока** при живой сессии (D-024); в ванили игрок есть. Kiln отдаёт модам «соединение есть, игрока нет».
- **Проверка покрытия заглушек:** скомпилировать исходники мода против `kiln-runtime.jar`. Для чужих jar без исходников нужен анализатор байткода — задел для этапа «анализатор jar».

Ограничения сейчас:
- HUD мода обновляется 20 раз в секунду (раз в тик).
- Нет Brigadier (чат-команд модов), нет экранов, рендера мира, сущностей, сети.
- Проверено только на macOS (Apple Silicon); Windows и Linux не запускались.

## План следующего этапа: настоящий мод с Modrinth

Цель — 1–2 чужих маленьких клиентских Fabric-мода под 26.3 **без Mixin**, скачанных как есть, работают в Horizon
через Kiln. Оценка — 1–2 недели.

1. **Анализатор jar** (`tools/kiln-scan`, 1–2 дня). Читает class-файлы мода и выписывает все обращения к
   `net.minecraft`, `com.mojang`, `net.fabricmc` (классы, методы, поля с дескрипторами) и наличие Mixin в
   `fabric.mod.json`. Сравнивает их со списком заглушек Kiln и выдаёт отчёт «работает / не хватает N членов».
   Это же основа будущего анализатора из этапа 3 видения.
2. **Выбор кандидатов** (полдня). Modrinth API: Fabric, 26.3, client-side, без Mixin, по скачиваниям. Прогнать
   анализатор и взять 1–2 мода с наименьшей нехваткой: скорее всего HUD-информеры (FPS, координаты, часы,
   броня).
3. **Генератор заглушек** (2–3 дня). Вместо ручного написания — генерировать классы-заглушки с точными
   сигнатурами 26.3 из `javap`. Тела «не поддерживается в Kiln» бросают понятную ошибку, руками пишутся только
   нужные методы. Тогда моды линкуются целиком, а падают только на реально неподдержанном вызове.
4. **Расширение моста** (3–5 дней): то, что попросят выбранные моды. Вероятно: позиция и инвентарь игрока,
   `getFps`, стили `Component`, больше методов `GuiGraphicsExtractor`, Brigadier (настоящий jar Mojang под MIT из
   библиотек Minecraft) для клиентских команд.
5. **Проверка**: тот же `proof.py` с модами, скачанными с Modrinth, плюс отчёт анализатора до и после.

Риски этапа: большинство модов используют Mixin; клиентским модам нужен рендер мира и экраны; модель «Java рядом
с игрой» не даёт синхронно спросить игру о том, чего нет в снимке. Снимок придётся расширять.

## Известные риски

1. ~~JVM не встаёт внутрь Horizon~~ — подтвердилось иначе: внутри Horizon запрещён `unsafe`, JVM в процессе игры невозможна. Обход — Java отдельным процессом (см. «Результаты спайка»).
2. **Ревью реестра.** Нативные моды мейнтейнеры читают построчно; запуск внешнего процесса `java` может не пройти. Запасной путь — релизы на GitHub и локальная сборка игроком.
2а. **Java у игрока.** Kiln ищет Java не старше той, под которую собраны моды (для таймера — 25; сам Kiln работает на 21+): настройка `java_home`, `KILN_JAVA_HOME`, `JAVA_HOME`, рантаймы лаунчера Minecraft, системные JDK. Лаунчер Horizon ставит Java для подготовки, где — ещё выяснить.
3. **Внутренние поля Horizon меняются** с каждым Nightly (достижения, пауза). Изолируем чтение в одном месте, проверяем на свежем Nightly.
4. **Fabric-моды используют Mixin.** Без Mixin работает лишь малая часть модов. Поддержка Mixin — ориентир, не обещание.
5. **TeaVM и рефлексия** — риск из исходного плана. При варианте 1 он снимается.
6. **Скорость сборки у игрока:** лаунчер предупреждает о 20–30 минутах; у альфы на Mac с Apple Silicon первая сборка заняла около 10 минут (INSTALL.md), дальше — несколько минут.

## Что мы узнали про API Horizon

Задел для этапа 2: чего не хватает и что неудобно.

### Нативные моды (то, на чём мы строим)
- Бандл = `horizon-mixin.toml` + `.rs`-файлы. `[[module]]` добавляет файл в игру как `crate::game::<name>`; `[[injection]]` вешает helper на функцию игры (`kind = "HEAD"` и др.) с привязками `bindings`.
- В модулях и helpers нельзя: внутренние атрибуты, `//!`-комментарии, `mod x;`, `include!`. Внешние крейты недоступны — только зависимости `horizon-client` (`serde_json`, `zip`, `ureq`, `chrono`, `sha2`, `log`, …).
- **Hook points v1:** `native_frame(elapsed)`, `native_tick()`, `native_hud(batch, corners)`, `native_key(key, pressed)`, `native_wheel(steps, claimed)`, `native_command(command, ran)`, `native_zoom`, `native_minimap`, `native_mods`, `native_settings`, `native_settings_click`. **v2:** панель предметов и рецепты.
- **Helpers:** `native_on`, `native_playing`, `native_window`, `native_player` (x y z, yaw, pitch, dimension), `native_frame_rate`, `native_clicks`, `native_mapping`, `native_mod_key`, `native_corner_shown`, `native_text_width`, `native_fill`, `native_text`, `native_chat`, `native_setting` / `native_set_setting` (по файлу на ключ в `horizon-mods/.horizon-mod-data/<id>/`), `native_data_dir`.
- **Не хватает (для Kiln и таймера):**
  - хука на входящие строки чата;
  - хука на получение достижения;
  - хука на смену измерения;
  - хука на вход в мир и выход из него;
  - helper'а игрового времени (`game_time`) и состояния паузы/загрузки.

  Пока обходим чтением полей `Game` (D-008).
- Отключённый в Options > Mods мод остаётся в сборке до следующей — каждый хук сначала проверяет `native_on`.
- У окна и у сервера одиночной игры — свои потоки и свой `Game`; каждый хук должен понимать, в каком он.
- **Инструменты:** `horizon-mods/native/tools/native.py` — `check` (apply + `cargo check` на коммите из `compatibility.json`), `build` (игра + `horizon-ctl`, профиль fast), `package` (`.hnmod`), `proof` (игра без окна на временных данных, управляется через `horizon-ctl`; нужен `--resources` с подготовленными файлами 26.3).

### Время, пауза, тики (из исходников Horizon)
- На паузе игра не вызывает тик вовсе (`if self.title.is_none() && !self.pause { self.tick() }`); кадр вызывается всегда.
- При лагах тики выбрасываются (`FixedStep::tick_fits`), поэтому «тики × 50 мс» отстаёт от реального времени.

### Достижения (из исходников Horizon)
- Прогресс хранится в `Game.adv.progress`; выдача — `Game::award` в `game/advancements.rs`.
- Сообщение в чат строится из `chat.type.advancement.{task,goal,challenge}` и `chat.square_brackets` на языке игрока, только при правиле `show_advancement_messages` (в 26.x правило называется так, а не `announceAdvancements`).

### WASM-API (удаляется, для истории)
- Был `horizon:mods@0.1.0`: capabilities `game-read`, `chat`, `hud`, `storage`, `command`, experimental `ui`, `input`, `render`, `recipes`. Хуки `init`, `tick`, `frame`, `command`, `chat`.
- Хук `chat` получал строки, только если чат не скрыт в настройках.
- Лимиты: storage до 64 файлов и 4 МиБ; `chat.show` до 8 строк за вызов.
